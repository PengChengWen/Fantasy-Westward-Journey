# 整体架构与目录设计

版本：0.1 · 2026-10-19 · 本文描述已建立的工程骨架及后续模块归属，不表示所有玩法已经实现。

## 1. 架构决定

采用一个客户端、一个进程内的分层模块结构。依赖箭头表示“引用”：

```text
Game.Client ───────→ Game.Application ───────→ Game.Domain
      │                     ↑
      └───────────→ Game.Infrastructure

ContentPipeline ──→ Game.Domain
Game.Domain.Tests → Game.Domain
```

Game.Infrastructure 引用 Application，实现由内层定义的接口。客户端 bootstrap 是组装入口，可以创建具体适配器；一般界面和战斗显示代码通过应用服务工作，不到处创建存档、Steam 或规则对象。

第一阶段不使用微服务、网络服务器、数据库服务器、完整 ECS、全局服务定位器或复杂依赖注入容器。模块先按文件夹隔离，只有依赖、测试或交付出现明确需求时再拆程序集。

## 3. 各层可以做什么

| 层 | 允许 | 不允许 |
| --- | --- | --- |
| Domain | 数值、回合、状态、编队、物品实例、纯规则 | Godot 节点、动画、Steam、文件读写、现实时间直接驱动战斗 |
| Application | 调用规则、协调一次游戏操作、定义存档／内容等端口 | 引用客户端或 Infrastructure 具体实现 |
| Infrastructure | JSON、文件、平台服务的具体实现 | 自己另算伤害、在读档时悄悄发奖励 |
| Client | 输入、UI、声音、镜头、角色动画、生命周期组装 | 在动画回调直接扣血、在按钮中散落打造与掉落公式 |
| Tools | 内容转换、校验和构建期输出 | 依赖游戏场景才能验证基础配置 |

Steam 的独立包装适配器以后放在 Infrastructure/Platform 的专用子模块；依赖引擎节点的初始化与回调桥接放在 game/platform。只有实际接入时才添加 Steam 包，不让当前本地模式承担原生依赖。

## 4. 回合战斗模块内部规划

Battle 后续按职责组织：State 保存当前状态；Commands 表示输入；TurnOrder 负责速度快照和排序；Resolution 负责行动结算；Effects 实现有限效果类型；Statuses 管理计时与限制；AI 生成合法指令；Events 输出结果。

指令由应用层接收，交给规则层检查。规则层依次结算存活、控制、替代策略、目标、资源、命中、伤害和状态，输出事件；表现层只播放结果。一个行动的结算结果一旦确定，动画倍速不能重新随机或再次扣血。

状态显式区分回合末与行动机会计数。宠物指令绑定具体实例和本次入场标识；替换旧宠时取消其未执行指令，新宠下回合行动，不能仅靠固定站位索引识别单位。

当前只落地 PartySlot 和 PartyRules：角色最多五名，每个槽位最多一只宠物，同一角色或宠物实例不得重复编队。尚未实现开战、伤害、回合、换宠与宠物存活行为。

## 5. 模块间数据与事务

内容定义与玩家实例分开。门派、技能、物品模板使用稳定内容 ID；人物、宠物和装备使用独立实例 ID；改中文显示名不能改变存档引用。

战斗快照只携带本场必要状态，不能直接操作整个背包或帮派对象。战斗结束后由应用用例统一结算经验、铜铢、掉落与任务进度，并使用结算 ID 防止重复发奖。

打造和炼妖通过一个应用用例校验材料、归属、随机状态与结果，成功时一起提交。跨模块事务先以进程内快照和明确提交边界实现，不引入分布式事务框架。

存档 DTO 与场景节点完全分离，只保存稳定状态和版本信息，不序列化 Node 引用、视图对象或回调。user:// 的实际绝对目录由客户端提供给文件适配器，文件层不需要引用 Godot。

## 6. 内容与资源流

当前 game/data/bootstrap.json 是初始规则数据源，包含七门派及五角色五宠上限。ContentPipeline 校验 schema、ID 和编成上限，并输出数量与源文件 SHA-256，不会生成未定义的技能效果。

后续技能、怪物、物品、任务等以独立内容表接入校验器；共用的配置契约在实际被多个模块使用时再提取，避免先建一个包含所有对象的巨型公共程序集。

运行资源放 game/resources，原始绘画与音频工程放 assets-source。面板、按钮、文字分层，UI 实现遵循 [UI设计与生成规范](UI设计与生成规范.md)。

世界节点连接、地图内部碰撞和地图美术分别维护。区域 ID 连接逻辑内容，场景路径属于客户端资源映射；不把 Godot 场景路径写成任务系统的唯一标识。

## 7. 构建与检查边界

Game.Core.slnx 不含 Godot 工程，可单独验证规则与工具；Game.slnx 包含客户端，用于有 Godot .NET 环境的开发与整体验证。

检查工程结构.ps1 检查已声明项目引用、核心代码显式引擎引用、启动资源、初始配置与文档链接。它不是完整 C# 静态分析器，不能替代编译、规则测试与引擎运行。

CI 当前执行核心构建和测试，不安装 Godot、不导出游戏、不发布 Steam。完整客户端检查和导出应在本地 M0 通过后单独增加，避免一个未验证的发布脚本误导使用者。

## 8. 实施顺序

1. 补齐开发 SDK 与 Godot .NET，完成已有骨架的编译、规则测试、启动场景和导出验证。
2. 在 Domain/Battle 实现最小回合和普通攻击，在 Application/Battle 添加推进用例。
3. 在 game/scenes/battle 接入占位视图与指令 UI，验证五角色五宠。
4. 加入连击、休息、群法、治疗、复活，再加入封印与其余门派。
5. 接奖励、背包、存档与一个地图任务，做出第一段完整流程。

在本稿基础上增加代码时，应优先添加真实用例与对应测试；不要为了填满目录编写没有调用者的通用管理器或假实现。
