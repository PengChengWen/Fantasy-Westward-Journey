# 《照夜山海》技术选型方案

版本：0.2 · 日期：2026-10-19 · 状态：建议方案，等待原型验证。文档使用中文命名。

适用设计：[玩法设计总案](玩法设计总案.md)、[世界地图与区域设计](世界地图与区域设计.md)、[七门派与回合制战斗设计](七门派与回合制战斗设计.md)。

## 1. 结论

推荐采用 **Godot 4.7.2 .NET + C# + 二维等距／斜俯视场景 + 数据驱动的回合战斗 + 本地版本化存档**。首发目标为 Windows x64 Steam 买断制单机。

Godot 负责画面、输入、地图、界面、音频与资源管理；独立 C# 模块负责战斗、装备、灵兽、任务与帮派规则；Steam 功能通过独立适配层接入。

初版使用本地文件保存配置与进度。当前业务没有必须引入 PHP、MySQL、Redis、游戏服务器或账户后台的需求；现有仓库放在 phpstudy 目录下，不影响它作为 Godot 游戏工程使用。

方案按一至三名开发者、以二维素材为主的独立游戏规划。团队技能、预算和美术方向尚未确认，因此这是本项目的推荐，不是对所有团队通用的最优解。

## 2. 选型依据

本项目主要技术压力来自大量规则、内容和存档兼容，而非大型三维渲染或实时联网。

- 七门派共享速度排序、行动、封印、恢复、变身和休息，需要一致的规则实现。
- 炼妖、随机词条、打造、掉落和帮派发展需要可复现、可校验的数据处理。
- 23 个区域适合按场景分别加载，不需要无缝开放世界。
- 任务、对话、商店、图鉴与编队界面较多，编辑效率和 UI 可维护性重要。
- Steam 接入、导出和存档升级应早期验证，避免内容做完后才发现发行阻塞。

优先级依次为：能做出完整可玩的版本、规则可靠、内容易扩展、构建可重复、性能满足目标设备。

## 3. 引擎比较

| 候选 | 对本项目的优势 | 主要代价 | 决策 |
| --- | --- | --- | --- |
| Godot .NET | 二维场景和 UI 可直接制作；C# 可分离规则模块；引擎采用 MIT 许可 | Steam 包装库与导出需自行验证；C# 依赖外部开发环境 | 首选 |
| Unity + C# | 团队若已有经验或可用资产，能减少部分制作成本；适合后续增加三维表现 | 引擎、插件与项目管理成本需结合实际团队衡量 | 已有成熟 Unity 经验或需要较多三维角色时优先重评 |
| Unreal Engine | 适合复杂三维画面与成熟三维内容流程 | 对当前二维回合制目标，框架与资产流程投入偏大 | 当前不选 |
| RPG Maker | 适合快速验证传统 RPG 事件和流程 | 本作的五角色、多灵兽、封印时序与经营 UI 需要较多定制 | 仅作为特定快速试验的候选 |

Godot 的 MIT 许可允许商业发行，但分发时须保留相应版权和许可声明，第三方组件与素材也需分别记录。[Godot 许可说明](https://godotengine.org/license/)

不以过时的“Unity 按安装收费”作为排除依据：Unity 已取消 Runtime Fee，实际订阅与使用条件应查看签约时的政策。[Unity 官方说明](https://unity.com/products/pricing-updates)

这里的生产效率比较是基于当前项目规模的判断，不是已测得的引擎性能结论。

| 领域 | 推荐技术 | 使用范围 |

| 动画 | AnimatedSprite2D、AnimationPlayer、Tween | 序列帧角色、特效时序、界面反馈 |
| 配置 | UTF-8 JSON + System.Text.Json | 技能、物品、掉落、任务、区域连接、文本 |
| 本地存档 | 版本化 JSON + 临时文件写入 + 备份 | 多槽位存档、迁移与损坏恢复 |

| 测试 | xUnit + 无图形模式场景检查 | 规则单测、存档迁移、配置与资源检查 |
| 版本管理 | Git；大体积二进制素材按需使用 Git LFS | 代码、文档、配置、场景和素材源文件 |
| 构建 | GitHub Actions，先以 Windows 构建为主 | 规则测试、配置校验、导出与构建产物归档 |

截至本稿查询，Godot Windows 下载页列出了 4.7.2 .NET。开工时先对这版执行最小验证，编辑器与 .NET 导出模板必须同版；后续升级通过专门分支验证，不自动跟随开发版。[官方下载页](https://godotengine.org/download/windows/)

.NET SDK、目标框架与引擎自带运行时是不同概念。不能仅因本机装有新版 SDK 就假定导出包兼容；应验证生成工程、测试项目、导出包与 Steam 包装库后，再记录具体 SDK 补丁号和依赖版本。本稿不声称这些组合已经构建通过。[Godot C# 说明](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html)

依赖锁定要求：记录引擎、模板、SDK、NuGet 包、Steam 包装库与原生 SDK 的版本；提交包锁文件；避免直接依赖可变的分支头。新增依赖必须能说明它解决的具体问题。

## 5. 工程结构

下列为选型阶段的简化结构。现已建立工程骨架，包含 Infrastructure 层和独立核心解决方案；以 [整体架构与目录设计](整体架构与目录设计.md) 为实际目录依据，环境验证状态见 [开发环境与工程检查](开发环境与工程检查.md)。文档继续中文命名；源码、资源路径与稳定内容 ID 使用统一的 ASCII 命名，方便工具链、跨平台和检索，游戏内显示文本使用中文本地化键。

```text
Fantasy-Westward-Journey/
├─ docs/                    中文设计文档
├─ game/                    Godot 工程
│  ├─ project.godot
│  ├─ scenes/               地图、战斗、UI 场景
│  ├─ scripts/              引擎交互与表现脚本
│  ├─ resources/            Theme、SpriteFrames、音频等资源
│  ├─ data/                 校验后打包的配置与本地化文本
│  └─ platform/             Steam 与本地平台适配
├─ src/
│  ├─ Game.Domain/          纯 C# 状态、规则、公式与事件
│  ├─ Game.Application/     游戏用例、存档 DTO 与服务接口
│  └─ Game.Infrastructure/  文件、配置和平台具体实现
├─ tools/
│  └─ ContentPipeline/      配置导入、检查、内容清单生成
├─ tests/
│  ├─ Game.Domain.Tests/
│  └─ Game.Application.Tests/
├─ assets-source/           素材源文件与授权记录
└─ build/                   本地导出目录，不提交发行包
```

采用普通分层与组合即可，不提前引入完整 ECS、插件市场、微服务或通用可视化技能编辑器。第一版先把有限的规则类型做清楚。

## 6. 规则与表现分离

```text
玩家指令／AI 策略
        ↓
应用层：验证编队、调用战斗或养成用例
        ↓
规则层：纯 C# 状态转换、数值结算、随机抽取
        ↓
战斗事件／事务结果
        ↓
Godot 表现：动画、音效、飘字、UI
```

规则层不引用 Godot 的 Node、SceneTree、动画和计时器，不调用 Steam，也不直接写磁盘。表现层不能在动画回调里额外扣血、掉落或发奖励。

规则层以明确状态变化生成事件，例如 ActionSkipped、DamageApplied、StatusAdded、UnitRevived。表现层按事件播放；跳动画或切换倍速只影响播放速度，不改变结算结果。

首版每次结算一条完整行动，再播放该行动事件，播放完成后处理下一条行动。无需实现完整事件溯源系统；战斗日志主要用于调试、复现和玩家反馈。

跨层访问通过小范围接口：ISaveRepository、IContentCatalog、IRandomSource、IPlatformServices。避免把所有功能放进一个全局管理器。

## 7. 回合战斗实现

### 7.1 状态与阶段

战斗状态包含单位、当前回合、资源、状态效果、待执行指令、行动队列和随机数状态。阶段依次为 RoundStart、CommandSelection、QueueBuild、ActionResolve、RoundEnd、BattleEnd。

我方编成固定按五名角色、每人最多一只在场灵兽建模，最多十个单位。灵兽实例记录 ownerCharacterId，角色在场宠物位引用 activePetInstanceId；归属和在场占用都需要唯一性校验，不能只维护一个无主人的全队宠物列表。

角色与宠物分别进入行动队列。召唤或换宠消耗主人的行动，旧宠离场时取消其未执行指令，新宠的 earliestActionRound 为下一回合；指令绑定具体单位实例与本次入场标识，不能因复用站位而转移到新宠。主人倒地、休息或被封不自动把状态传播给宠物。比武集成样例覆盖双方各十个单位，并检查布局、结算与动画播放时间。

速度在提交阶段结束时形成快照，之后的速度增益从下一回合排序起生效。同速抽签使用战斗随机流；AI 通过与玩家相同的指令验证器提交行动。

行动执行依次处理：单位存活与硬性失能 → 已声明指令是否可用 → 合法替代策略 → 目标与资源 → 支付成本 → 命中与分段效果 → 倒地和状态变化 → 事件输出。原指令无法执行不意味着获得额外行动。

保护关系在提交阶段按设计建立。若执行前保护者倒地或进入禁止保护的状态，立即失效；不能由动画出现的位置决定是否保护成功。

### 7.2 技能与状态模型

技能配置描述目标规则、成本、前置条件、效果列表、冷却及施放后状态。效果由有限的类型实现，例如 PhysicalDamage、MagicDamage、FixedDamage、Heal、Revive、ApplyStatus、Dispel、ModifyResource。

特殊技能通过专用规则组合，不把任意脚本字符串放进配置执行。七门派可优先复用这些组合：

| 门派 | 规则组合 |
| --- | --- |
| 执衡院 | 血线检查 + 气血成本 + 分段物伤 + 下回合休息 |
| 百骸谷 | 兽相检查 + 多目标或分段攻击 + 形态到期 + 休息 |
| 听潮阁 | 目标筛选 + 群法／单法 + 真气处理 |
| 绛罗坊 | 速度增益 + 双封 + 固伤 + 毒 |
| 绘契司 | 招式标签限制 + 降防 + 睡眠唤醒 |
| 济世院 | 即时治疗 + 增益 + 复活 |
| 照灯坊 | 即时治疗 + 后续恢复 + 复活 + 固伤 |

每种状态显式声明计时基准，区分：当前回合末、未来回合末、目标行动机会、施法者行动机会。冷却使用可再次施放的回合编号；不能统一在回合末简单减一。

休息、睡眠、变身到期、连续控制清醒窗口和首领压制分别建模。连击每段独立结算，目标倒地后中止，不自动把余下攻击转移给其他敌人。

### 7.3 确定性与复现

数值主干优先使用整数和有明确舍入点的定点倍率；例如万分比倍率用整数表示，较大乘法使用足够宽的中间类型并检查溢出。表现插值可以使用浮点数。

固定随机算法及其版本，保存种子与当前状态，不把特定运行时 Random 的内部实现当作跨版本协议。战斗、掉落、地图事件、打造和炼妖使用不同随机流，动画随机不影响规则随机。

复现记录包含规则版本、配置哈希、初始快照、指令与随机状态。同版本同输入应得到同结果；跨规则版本的旧回放不承诺直接兼容。

### 7.4 AI 与难度

首版采用条件优先级与评分策略：抢救、解控、续变身、封关键单位、集火、清场、回蓝。根据公开状态决策，不读取玩家尚未执行且未公开的指令。

敌方强招提示作为公开战斗信息记录，不由 UI 临时猜测。难度通过策略、编成和资源压力调节；数值调整放在明确配置中。

## 8. 配置与内容制作

JSON 是运行时规则配置的单一来源，Godot Resource 用于贴图、音频、Theme 和场景等引擎资产。避免同一技能数值同时存在 JSON 和 Resource 中。

初期直接编辑结构化 JSON。数值表数量增加后，可加入 CSV／表格导入工具，将策划表单向转换为 JSON；不要双向手改后再靠人工合并。只有实际需要编写该导入工具时才选择额外表格依赖。

每项内容使用不可随改名变化的稳定 ID，例如 sect_zhiheng、skill_break_formation、map_qinghe。显示名称和描述放入文本表；改技能中文名不修改存档引用。

构建前检查：ID 唯一、引用存在、枚举合法、概率范围、权重和、掉落表无非法循环、目标数合理、任务前置无死循环、区域入口存在、技能效果与状态标签兼容。校验失败不得生成发行包。

输出 content_manifest，记录配置版本、哈希和内容 ID；调试日志与存档记录该清单版本，便于定位问题。

## 9. 世界地图与场景

世界关系图是一张内容图：节点是区域，边声明入口、交通方式和剧情条件。它与区域内部坐标、碰撞和美术布局分开保存。

23 个区域分别制作场景，门派驻地、帮派院落和副本内部按需要作为子场景。进入新区域时保存旧区域的必要状态，加载目标场景并选择出生点；不存在的入口回到安全点并记录错误。

地图制作采用二维分层：地面、道路、建筑主体、可遮挡前景、交互标记。可使用手绘背景与可复用瓦片混合，TileMapLayer 不要求所有美术都做成规则小方块。[Godot TileMapLayer 说明](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)

点击移动先使用 AStarGrid2D，八方向移动并禁止穿越障碍角。逻辑寻路格与等距画面坐标经统一转换；Y 排序以角色脚点为准。动态 NPC 占位更新到独立阻挡层，不反复重建整张地图。[AStarGrid2D 文档](https://docs.godotengine.org/en/stable/classes/class_astargrid2d.html)

如果验证后发现手绘曲线路径与规则网格明显不匹配，再把寻路适配器替换为 NavigationRegion2D；保持玩法层只接收路径点，不绑定具体算法。

首版以 Compatibility 渲染器作为二维桌面原型候选；只有效果或性能验证表明需要时再更换。最终最低显卡、系统和内存要求由导出包实测决定。

## 10. 美术、动画、界面与音频

- 美术：斜俯视二维角色，地图手绘分层。第一阶段用占位素材验证，确定镜头尺度与角色像素尺寸后再批量制作。
- 角色：优先使用统一规格的多方向序列帧和 SpriteFrames；不在基础版同时引入多个骨骼动画插件。方向数、动作数、角色换装层数先做样板估算制作成本。
- 特效：AnimationPlayer 编排，Tween 做过渡；以规则事件驱动。战斗倍速、跳过和窗口失焦不得改变规则。
- UI：使用 Control、Container 和共享 Theme；布局通过锚点与容器适配，不按每个窗口硬编码固定坐标。
- 文本：简体中文优先，游戏内文本使用本地化键；验证中文长句、数字变化、字体授权和缺字回退。
- 操作：鼠标键盘为首要输入，指令选择与菜单保留统一焦点导航接口，为后续手柄适配留空间；不提前宣称 Steam Deck 已兼容。
- 声音：短音效采用 WAV，长音乐优先 Ogg Vorbis，设音乐、环境、战斗、UI 独立音量总线。

原型 UI 以 1920×1080 为主要检查尺寸，同时检查 1280×720 和超宽窗口。字体、按钮与面板应可缩放；这是布局验证目标，不是最终最低分辨率承诺。

## 11. 打造、炼妖、背包与帮派

养成系统也放进纯 C# 规则模块。定义数据与实例数据分开：物品模板只保存基础规则，装备实例保存实例 ID、词条、器灵与绑定；灵兽实例保存血脉、技能、成长、习性和共育疲劳。

每次打造或炼妖形成一笔游戏内事务：先校验完整输入，再一次性扣材料、推进随机流、生成结果并写入内存状态，随后生成待保存快照。失败不得出现扣一半材料、结果未生成或亲本误删除。

提交事务后触发自动存档；保存失败时保留内存进度并提示重试，不悄悄回退部分资源。仅靠本地存档不能阻止玩家回档，不把防作弊作为离线单机第一版目标。

帮派成员用稳定实例 ID 管理，同一个成员不能同时在岗位、探索队与玩家出战队中重复贡献。冒险完成推动帮派回合，不读取现实时间计算离线损失。

## 12. 任务、对话与世界变化

首版使用有限状态任务图和本地文本配置：未接取、进行中、可交付、已完成、已失败／关闭。条件由可组合类型表达，例如拥有物品、区域到访、事件完成、关系阈值。

对话节点关联文本、选项、条件和效果。任务效果通过统一用例修改状态，不允许对话节点自行跨层写文件或直接发放未经校验的奖励。

关键奖励、地图解锁与伙伴加入使用幂等标记，重复读取、重复交互或读档恢复不能重复领取。任务分支对商店、商路和鬼患的影响保存为世界标记。

先用简单工具预览任务图；当实际对话量证明需要更强编辑器时再评估专门对话工具，不把第三方叙事运行时列为开工前置。

## 13. 存档与版本迁移

存档写入 Godot 的 user:// 可写目录，不写进程序安装目录或只读资源包。[Godot 文件系统说明](https://docs.godotengine.org/en/stable/tutorials/scripting/filesystem.html)

存档内容包括：schemaVersion、gameVersion、规则版本、内容清单哈希、角色与灵兽实例、背包、任务、世界标记、帮派、地图安全点、随机流状态。每槽位携带可用于冲突判断的 saveId、revision、父 revision 与摘要信息。

初版只允许在安全点、战斗结束和稳定的场景边界保存，不承诺战斗中断点续存。以后增加战斗内保存时，必须同时持久化行动阶段、剩余队列与随机状态。

写入流程：生成不可变快照 → 序列化并做结构校验 → 写同目录临时文件 → 刷新到磁盘 → 尝试原子替换正式文件 → 保留上一份可读备份。替换失败保留旧档与临时文件，提示保存失败；具体文件 API 的行为需在目标系统测试，不能仅凭命名保证原子性。

读取流程：优先校验正式档 → 失败则读取备份并提示 → 按 schemaVersion 逐级迁移 → 检查内容引用 → 载入游戏。较新版本存档不能被旧版本覆盖；缺失必要内容时给出明确说明。

主线关键实例 ID 不重新随机生成。改名不改 ID；删除内容保留替代映射或可解释的兼容路径。校验摘要用于发现意外损坏，不作为防修改或加密保护。

提供多个手动槽位与滚动自动存档。默认不加密，不为压缩或二进制格式增加迁移难度；达到实际体积或加载瓶颈后再评估。

## 14. Steam 接入与云存档

Steamworks.NET 是面向 C# 的 Steamworks API 包装库，也可用于非 Unity 的 C# 应用；本项目计划在 Godot 中通过独立适配层使用，但必须验证原生库加载、回调泵、初始化、退出和导出目录结构，不能把它当作已验证即插即用插件。[Steamworks.NET 项目说明](https://github.com/rlabrecque/Steamworks.NET)

引入 IPlatformServices，提供 LocalPlatformServices 与 SteamPlatformServices。核心规则不依赖平台对象；开发构建可在没有 Steam 的情况下完成完整本地流程。Steam 初始化失败时，平台专属功能降级并记录原因，不损坏本地存档；发行构建的启动策略需要使用本项目 App ID 实测。

首版平台功能顺序：正确启动退出 → 成就与统计 → 云存档 → 其他展示功能。暂不接创意工坊、联机大厅、交易市场或全球竞技排名。

云存档建议先验证 Auto-Cloud，它可通过 Steamworks 配置同步指定文件。同步不是游戏存档的替代品，只包含正式存档、必要摘要与兼容信息；临时文件、日志和机器图形设置不进入同步集合。[Steam Cloud 文档](https://partner.steamgames.com/doc/features/cloud)

Auto-Cloud 冲突由 Steam 同步流程参与处理，游戏不能假定总能同时拿到两份文件。游戏只在实际拿到两条存档分支时显示摘要并保留副本；不只用设备时间认定新旧。验证离线游玩后上线、两台设备交替、写入中断和版本不同的情况。

Steam 凭据、发布令牌及账户信息不放入仓库；开发用 App ID 文件不按调试方式直接打入正式包。Steam API 包装库及 SDK 的采用条件分别遵循其条款，不因包装库开源而推定全部 Steam 材料可公开再分发。

## 15. 测试与可观测性

高价值测试优先覆盖已经定义的规则，而不是简单属性读写：

1. 三连击血线检查、成本扣除、分段击倒中止与下一回合休息。
2. 变身的四次行动机会与休息、连击结束形态之间的交互。
3. 封印目标已行动／未行动时的计数差异，睡眠受到直接伤害唤醒，持续伤害不唤醒。
4. 复活不刷新行动、冷却、真气；保护者失效时的目标处理。
5. 首领压制与连续控制清醒窗口，敌我规则一致。
6. 固定种子和输入复现同一战斗，改变动画倍速不改变结果。
7. 打造、炼妖材料不足时无部分扣除，成功时无重复发放。
8. 存档损坏恢复、旧 schema 迁移、较新档拒绝覆盖与跨设备分支识别。
9. 任务奖励幂等，帮派成员不能重复占用岗位与出战位置。
10. 每名角色最多一只在场灵兽，同一实例不能重复编队；主人倒地后灵兽独立行动，换宠取消旧指令且新宠当回合不能行动。

纯规则测试使用 dotnet test；Godot 场景、资源引用、中文 UI、导出后的输入音频与原生库另做集成检查。无图形模式测试不能证明真实图形、音频与 Steam Overlay 正常。

调试日志记录回合、行动 ID、失败原因、状态变更与配置版本。正式日志限制大小并滚动；不默认上传玩家存档或个人信息。

## 16. 性能与构建目标

首版目标是在指定参考 Windows 设备上，主要地图和常规战斗达到 1080p、60 FPS；这仍需设备与真实素材验证。先记录参考硬件，再形成最低配置声明。

战斗逻辑、资源加载、存档和 UI 分别测量，不把长动画误判为结算慢。重点检查进入地图时的阻塞、频繁实例化、贴图内存、中文文本布局和大量图鉴列表。

规则结算避免依赖帧率；初期在主线程完成短事务即可。确认存在可测卡顿后，再将纯规则计算或序列化移至后台，Godot 场景树操作仍在合适线程执行；不为回合制预先引入复杂多线程同步。

构建产物携带版本号、Git 提交号和内容清单。CI 依次执行依赖恢复、编译、测试、内容校验、Godot 导入与导出、产物校验。Steam 上传使用独立发布步骤，不让普通提交自动发布给玩家。

导出包要在未安装开发 SDK 的干净环境验证，确保所需运行组件与原生库齐全；不能只在编辑器里运行成功就宣布可发行。[Windows 导出文档](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)

## 17. 分阶段实施与验收

| 阶段 | 交付内容 | 通过条件 |
| --- | --- | --- |
| M0 工具链验证 | Godot .NET 空工程、纯 C# 模块、测试项目、Windows 导出、Steam 适配最小试验 | 编辑器与导出包均可启动；纯规则测试可运行；离线本地模式可用；记录准确版本与许可 |
| M1 战斗原型 | 七门派基础效果、五角色五灵兽编成、归属与换宠、AI、日志与倍速 | 使用占位画面完成若干种典型战斗，含双方各十个单位；休息、封印、复活、持续恢复与换宠规则通过测试 |
| M2 首段完整流程 | 青禾埠、听潮湾、断桅礁、芦汀原、昭宁京，接入捕宠、掉落、打造与存档 | 从接任务到冒险、养成、再次挑战形成闭环，退出重启能继续 |
| M3 内容生产 | 区域、任务与技能配置工具，炼妖、帮派、比武 | 新内容主要通过配置与场景接入；奖励、成员和资源事务稳定 |
| M4 完整游戏 | 后续区域、副本、神兽、飞升渡劫化圣、结局 | 主线可完整通关；旧存档可迁移；普通养成也能通关 |
| M5 Steam 发行验证 | 成就、云同步、发行构建、干净机测试与演示包 | 导出包及平台功能验收，达到实测性能目标，发行素材与条款记录完整 |

Steam 原生库和导出可行性在 M0 就验证，云同步和完整发行测试在 M5 收尾，不能把所有平台风险拖到最后。

此处按验收结果划分，不根据尚未确认的人力和素材量承诺开发周数。真正决定周期的将是区域内容、角色方向动画、任务文本和测试覆盖，而不只是代码行数。

## 18. 风险与调整条件

| 风险 | 处理方式 | 何时重新选型 |
| --- | --- | --- |
| Godot .NET 与 Steam 包装库导出不兼容 | 在 M0 验证并锁版本；适配层隔离；必要时评估其他包装方式 | 最小包仍不能稳定启动与退出时 |
| 二维多方向角色和换装素材量过大 | 用一个完整样板估算，减少初版外观组合、复用动画规格 | 若决定大量三维角色／换装，重新比较 Godot 三维与 Unity |
| 配置驱动变成任意脚本执行器 | 保持有限效果类型与校验器，特殊招式用受测试的代码规则 | 实际内容持续受限时，再增编辑能力 |
| 战斗规则出现边界争议 | 更新门派文档并新增对应规则测试，明确状态时序 | 不靠引擎切换解决规则含糊 |
| 存档跨版本损坏 | schema 迁移、备份、稳定 ID、迁移样本 | 数据规模出现实测瓶颈后再考虑 SQLite／二进制格式 |
| 团队已有大量 Unity 成熟经验与资产 | 比较首段完整流程的实际制作成本 | 在 M0 后、批量制作内容前作最终引擎决策 |

## 19. 当前状态与下一步

本仓库已从设计文档阶段推进到工程骨架阶段：建立 Godot 启动场景、C# 分层项目、初始配置工具、规则测试源码及 CI。尚未安装 Godot 或开发 SDK，未引入 Steam SDK，尚未验证游戏运行、性能与发行导出；不能将骨架视为已完成的战斗系统。

下一步建议执行 M0：先拿到一个能够在编辑器外启动、运行一回合占位战斗、写入并读取存档的 Windows 包，再批量制作地图与素材。技术选型在这个小范围验证通过后冻结。
